# ADR-0019: Edge device-client management

- Status: **ACCEPTED (slice A — enrol / approve / monitor)**
- Date decided: 2026-10-22
- Deciders: socaya
- Related: ADR-0002 (DHIS2 pin), ADR-0015 (orgUnit binding),
  ADR-0017 (TLS + PII), ADR-0018 (capture workflows), post-1.0
  roadmap Initiative 1

## Context

Up through `der-1.2.0-alpha.1`, a "device" is just a logged-in
browser session. There is no first-class device identity, no
enrolment handshake, no admin fleet view. The project proposal
promises *enrol site-level client and workflow dependencies,
approvals, and monitoring*. The post-1.0 roadmap scopes this as
Initiative 1.

ADR-0018 slice A left room for `owner_device_id` on workflow steps;
peer-to-peer chains (Initiative 3) need device pairs. This ADR
lands the device-identity primitive that both lean on.

## Decisions (slice A, pre-approved per roadmap D6..D8)

| # | Decision | Chosen |
|---|---|---|
| D6 | Device identity source | **Installation UUID** generated by the client on first launch and persisted in `localStorage`. Hardware fingerprinting rejected (privacy-adversarial, OS-specific, blocked by browser hardening). Per-device TLS certs rejected for slice A (distribution overhead). |
| D7 | Approval model | **Manual admin approval only.** Auto-approve-from-LAN is tempting on well-controlled hospital networks but opens a mistaken-trust path operators cannot audit without a lot of extra wiring. One click per device is cheap for pilot volumes. |
| D8 | Workflow-dependency semantics | **Store but don't act on** in slice A. The schema has a generic `dependency_kind` enum (`APPROVES`, `FORWARDS`, `SUPERVISES`) so Initiative 3 (peer-to-peer chains) and Initiative 10 slice B (device-level step owners) can both read it without an additional migration. |

## Lifecycle

```
    client first-launch
          │
          ▼
    POST /devices/enroll                 ─────► edge_device row created
    (installation UUID + user agent)     ─────► status = PENDING
                                                 enrolment_token_hash set
          │
          ▼  admin opens EA-DVC-01
          │
          ▼  admin clicks Approve on the row
    POST /devices/{id}/approve           ─────► status = APPROVED
                                                 approved_by / approved_at set
          │
          ▼
    client periodic heartbeat
    POST /devices/{id}/heartbeat         ─────► last_seen_at updated
    (any authenticated user)
          │
          ▼  admin can SUSPEND or REVOKE at any time:
    POST /devices/{id}/suspend
    POST /devices/{id}/revoke
```

Devices in state `REVOKED` cannot heartbeat (403 with
`code=DEVICE_REVOKED`). `SUSPENDED` is identical but reversible via
Approve.

## Schema (V015)

```sql
edge_device (
    device_id             UUID PRIMARY KEY,
    assigned_user_id      UUID REFERENCES edge_user(user_id),
    enrolment_token_hash  TEXT,
    enrolled_at           TIMESTAMPTZ NOT NULL DEFAULT now(),
    approved_by           UUID REFERENCES edge_user(user_id),
    approved_at           TIMESTAMPTZ,
    last_seen_at          TIMESTAMPTZ,
    user_agent            TEXT,
    firmware_version      TEXT,
    status                TEXT NOT NULL CHECK (status IN
                               ('PENDING','APPROVED','SUSPENDED','REVOKED'))
                               DEFAULT 'PENDING'
);

edge_device_dependency (
    device_id             UUID NOT NULL REFERENCES edge_device(device_id)
                                               ON DELETE CASCADE,
    depends_on_device_id  UUID NOT NULL REFERENCES edge_device(device_id)
                                               ON DELETE CASCADE,
    dependency_kind       TEXT NOT NULL CHECK (dependency_kind IN
                               ('APPROVES','FORWARDS','SUPERVISES')),
    PRIMARY KEY (device_id, depends_on_device_id, dependency_kind),
    CHECK (device_id <> depends_on_device_id)
);
```

The `enrolment_token_hash` carries the Argon2id hash of a
short-lived enrolment token the client receives in the `/enroll`
response; the server never stores the raw token (same pattern as
sessions). Slice A does not actually enforce the token on
heartbeat — the cookie-session auth is sufficient — but the hash is
captured so Initiative 3 (peer-to-peer) can use it as a pairing
secret without a schema change.

## REST surface

| Method | Path | Role |
|---|---|---|
| POST | `/edge-api/v1/devices/enroll` | any authenticated user (self-enrol) |
| GET | `/edge-api/v1/devices` | ADMIN+ |
| GET | `/edge-api/v1/devices/{id}` | ADMIN+ |
| POST | `/edge-api/v1/devices/{id}/approve` | ADMIN |
| POST | `/edge-api/v1/devices/{id}/suspend` | ADMIN |
| POST | `/edge-api/v1/devices/{id}/revoke` | ADMIN |
| POST | `/edge-api/v1/devices/{id}/heartbeat` | any authenticated user (self) |

Error shape:

```json
HTTP 403 (revoked):
{ "code": "DEVICE_REVOKED", "message": "..." }
```

## Admin UI

New screen bundled into `EACoreScreens.tsx`:

- `EADeviceFleet` (EA-DVC-01) at `/devices` — list every enrolled
  device with status, user agent, last-seen, assigned user,
  Approve/Suspend/Revoke buttons depending on current state. Delete
  for `REVOKED` rows.

The dependency editor (EA-DVC-02) is **slice B** — the schema is
in place now so Initiative 3 (peer-to-peer) and Initiative 10
slice B (device-level owners) can start reading from it.

## Device-client integration (minimal)

The client gains a tiny `DeviceEnrollment` component mounted inside
`AuthProvider`'s AUTHENTICATED branch. On first mount per browser
install:

1. Read `der_device_id` from `localStorage`; if absent, generate a
   fresh UUID and persist it.
2. Call `POST /devices/enroll { deviceId, userAgent }`.
3. The server upserts the row at `status=PENDING` on first write and
   is a no-op on subsequent calls.
4. The client periodically calls `/heartbeat`.

The client does **not** block the UI while awaiting approval in
slice A — writes still work (ADR-0016 approval handles that layer
when a workflow is active). "Awaiting approval" UI gating ships
with Initiative 3 / Initiative 10 slice B when the device identity
actually controls behaviour.

## Not in scope (slice B promises)

- EA-DVC-02 dependency editor UI.
- `/devices/{id}/dependencies` CRUD endpoints.
- Device-identity-driven step ownership in workflows (needs
  Initiative 10 slice B).
- Device-to-device trust (Initiative 3).
- MDM integration / enterprise fleet management.
- Push notifications to a specific device.
- Per-device permissions (role still lives on the user).

## Consequences

- Pilot operators now see every browser install in EA-DVC-01 and
  can suspend lost / stolen devices.
- The admin UI gains one new left-nav item.
- The client gains one new `edgeApi` call (`enrollDevice`) and one
  periodic (`heartbeatDevice`) call. Heartbeat cadence is configurable
  via `der.device.heartbeat-seconds`, default 300.
- Admin UI role matrix stays unchanged: all approve/suspend/revoke
  actions are `ADMIN`-only.
