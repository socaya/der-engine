# EA-23 — Resolution

> **Project baseline:** Design and Implementation of a Conflict-Aware Edge Synchronisation Runtime for Offline-First Distributed DHIS2 Workflows. **DER target:** DHIS2 2.43+, initially pin one tested 2.43.x patch. **Status:** Design specification; neither DHIS2 integration nor passing tests is asserted. **Audience:** Student developer, supervisor, reviewers and future maintainers.

## Audience and purpose
**Application:** `admin-ui`. **Domain:** server runtime, metadata, synchronisation or security administration. This screen supports `resolution` and shall preserve the fundamental separation of local working state from central reconciliation. The design is required; implementation state is **specified**, not built.

## Primary data and actions
The user must be able to inspect and administer the appropriate DER-managed resource; any mutation must be role-restricted and audited. Display entity and site context, relevant scope, local transaction status, validation messages and last trustworthy refresh. Use only configured and authorised records, backed by the relevant DHIS2 or DER API; do not invent success states or unsupported application operations.

## Layout
Desktop: title, context toolbar, filter/actions, main form or table and supporting status. Tablet: reorganised single/two-column content with touch targets. Mobile: prioritised task flow and readable controls, without deleting safety-critical status or validation.

## Required UI states
Initial/loading; empty; data loaded; editing; input invalid; saving; locally committed; pending central; central accepted/rejected where relevant; conflict/review; permission denied; edge unavailable; central WAN unavailable (but edge still usable). Hide irrelevant status states rather than fabricate them.

## Roles and security
Enforce endpoint-level and screen-level permission checks. Do not expose central credentials, complete sensitive payloads or unauthorised OU/program records. Administrative mutations require explicit confirmation, reason and audit entry.

## Acceptance tests
1. Screen renders required labels, fields, route context and responsive layouts.
2. Correct authorised API data appears; forbidden user/action is rejected by API and UI.
3. Validation, loading, empty and error states are accessible and understandable.
4. With WAN disabled and edge LAN operational, permitted local operations remain usable; if screen performs central-only administration, it explains the limitation without false success.
5. Saved locally is never described as synchronised centrally before verified outcome.
6. Screen has a traceability entry and Playwright/interaction evidence before marking `verified`.
